BiddingFlow 백엔드-프론트 통합 작업 로그
정리 기준일: 2026-09-02
대상: SKN31-FINAL-3Team 백엔드와 SKN31-FINAL-front 프론트의 통합 작업

※ 이 문서는 백엔드-프론트 연결 작업을 시작한 이후의 현재 작업 트리, 테스트 결과,
   실행 중 확인한 사항을 기능 단위로 재정리한 기록이다.
※ API Key, Secret, DB 비밀번호, JWT 키 등 실제 비밀 값은 기록하지 않았다.
※ Git 커밋 단위의 변경 일지가 아니라 현재 로컬 구현을 기준으로 한 통합 작업 요약이다.


1. 전체 통합 방향
------------------

- ERPNext를 구매 원문 문서의 기준 시스템(Source of Truth)으로 유지했다.
- 별도 PostgreSQL에는 ERPNext가 직접 표현하기 어려운 다음 운영 상태를 저장하도록 분리했다.
  · MR별 현재 구매 단계와 실행 상태
  · 사용자 개입 대기 작업(Interrupt Task)
  · 반려·복귀·재시도 이력
  · 알림과 실시간 이벤트
  · 배송/수령 및 공급사 평가 연결 상태
  · AI 판단 결과와 실행 기록
- 프로젝트 전제인 “MR 1건 = 품목 1개”를 프론트 표시 및 백엔드 프로젝션의 기본 단위로 삼았다.
- 프론트가 LangGraph 노드를 직접 호출하지 않고 FastAPI의 안정된 API 계약만 호출하도록 계층을 분리했다.
- 화면의 단계 이동은 프론트 임의 상태가 아니라 ERPNext 문서 상태 + PostgreSQL 실행 상태의 조합으로 계산하도록 구성했다.


2. 인증 및 세션 기반 연결
-------------------------

- auth_service 모듈을 기준으로 로그인, 로그아웃, Access Token, Refresh Token 흐름을 구성했다.
- ERPNext 로그인 검증 결과와 BiddingFlow 사용자 세션을 연결할 수 있도록 했다.
- Refresh Token은 PostgreSQL 인증 저장소에서 회전·폐기할 수 있는 구조로 구성했다.
- 보호가 필요한 구매 API에는 FastAPI CurrentUser 의존성을 적용했다.
- 프론트는 API 요청 시 Access Token을 보내고, 만료 시 Refresh 흐름을 거친 뒤 요청을 재시도할 수 있는 기반을 마련했다.
- 프론트의 백엔드 주소는 고정된 127.0.0.1 문자열 대신 환경변수로 지정할 수 있게 했다.

4. 프론트가 호출하는 구매 REST API
----------------------------------

FastAPI에 다음 구매 API를 연결했다.

- POST /api/procurement/cases/sync-drafts
  ERPNext의 Draft MR을 동기화하고, 필요 시 기존 캐시와 대조한다.

- GET /api/procurement/cases
  상태·단계·종료 포함 여부·페이지 범위에 따라 구매 케이스를 조회한다.

- GET /api/procurement/cases/{case_id}
  한 MR의 상세정보, 사용자 작업, 배송정보를 함께 조회한다.

- POST /api/procurement/cases/{case_id}/start
  사람이 검토한 MR의 AI 구매 워크플로 실행을 시작하거나 실패 체크포인트에서 재개한다.

- POST /api/procurement/cases/{case_id}/reject
  구매 작업자의 반려 사유를 ERPNext와 운영 DB에 반영한다.

- POST /api/procurement/cases/{case_id}/quotation-deadline
  견적 마감일 연장과 관련 상태 변경을 처리한다.

- GET /api/procurement/tasks
  현재 사용자에게 필요한 개입 폼 목록을 조회한다.

- POST /api/procurement/tasks/{task_id}/answer
  폼 응답을 저장하고 중단된 LangGraph 실행을 재개한다.

- GET /api/procurement/notifications
  알림 목록과 읽지 않은 알림을 조회한다.

- POST /api/procurement/notifications/{notification_id}/read
  알림을 읽음 처리한다.

- GET /api/procurement/events
  PostgreSQL LISTEN/NOTIFY를 이용한 인증된 SSE 실시간 알림 스트림이다.

- GET /api/purchase/items
  ERPNext에 실제 등록된 Item 목록을 조회한다.

- GET /api/purchase/items/{item_code}/specifications
  해당 Item의 그룹별 규격 필드와 실제 값을 조회한다.

주요 파일

- backend_logic2/integrations/erp_client.py
- backend_logic2/services/workflow_service.py
- backend_logic2/services/workflow_projection.py


5. ERPNext 수신 방식: 폴링과 웹훅 전환
-------------------------------------

- MR 수신 방식을 MR_INGEST_MODE 환경변수로 바꿀 수 있게 했다.
  · polling: 로컬 개발 및 공용 네트워크 환경에서 사용
  · webhook: AWS에 백엔드를 배포하고 ERPNext가 접근 가능한 주소가 생긴 뒤 사용
- polling 모드에서는 서버 시작 시 기존 Draft MR을 한 번 동기화하고 이후 짧은 주기로 신규 Draft를 확인한다.
- 동기화 시 ERPNext에서 사라진 문서를 무조건 삭제하지 않는다.
  · 명시적인 404 또는 docstatus=2(Cancelled)인 경우에만 종료 상태로 정리
  · 일시적인 ERP 통신 오류는 MR 삭제로 오판하지 않음
- 웹훅 전환을 위한 엔드포인트를 미리 구성했다.
  · POST /api/webhooks/erpnext/material-request
  · POST /api/webhooks/erpnext/purchase-receipt
  · POST /api/webhooks/erpnext/item
- 웹훅은 로그인 사용자 토큰이 아닌 별도의 서버 간 Secret 헤더로 인증한다.
- 웹훅 이벤트 ID를 이용해 ERPNext의 재시도 요청을 중복 실행하지 않도록 했다.
- /api/health에서 현재 수신 모드, MR 폴러, 대체품 응답 폴러의 작동 여부를 확인할 수 있게 했다.

현재 개발 환경 상태
- MR 수신: polling 모드
- MR 폴러: 활성
- 대체품 응답 폴러: 활성
- AWS 배포 후 할 일: ERPNext Webhook URL을 AWS FastAPI 주소로 변경한 뒤 MR_INGEST_MODE를 webhook으로 전환


6. LangGraph 구매 흐름과 상태 프로젝션
--------------------------------------

- 기존 팀원 노드 코드를 최대한 유지하면서 프론트가 해석할 수 있는 표준 단계/상태로 투영하는 계층을 추가했다.
- process_graph.py와 process_commands.py의 Command(goto=...) 흐름을 그대로 활용했다.
- 주요 흐름을 다음과 같이 연결했다.
  1) MR 검토 시작
  2) Item 및 대체품 확인
  3) 요청자의 대체품 선택 대기
  4) 구매/입찰 판단
  5) 기존 또는 신규 공급사 탐색
  6) RFQ 대상 공급사 선택 및 이메일 보완
  7) RFQ 생성·발송 및 견적 회신 대기
  8) 견적 비교와 최종 공급사 선택
  9) 발주 시작과 PO 발송 전 사용자 승인
  10) PO 생성·Submit·이메일 발송
  11) Purchase Receipt 수신 및 공급사 평가 가능 상태 전환
- 각 중단 지점은 단순 input() 대신 task 레코드와 form_schema를 생성하는 방향으로 연결했다.
- 사용자 답변이 들어오면 task 버전과 상태를 확인한 뒤 LangGraph 체크포인트를 재개한다.
- 체크포인트의 실제 next 노드와 DB에 표시할 stage/status가 어긋나지 않도록 projection 서비스를 추가했다.

7. 실패 후 재시작 및 체크포인트 복구
-------------------------------------

- AI 실행 중 환경변수나 외부 API 문제로 실패한 MR이 영구적으로 멈추지 않도록 재시도 흐름을 추가했다.
- FAILED 케이스에 유효한 LangGraph 체크포인트가 있으면 ERPNext 문서가 이미 Submitted 상태여도 재시작을 허용한다.
- 재시도 시 MR 처음부터 다시 실행하지 않고 checkpoint.next 위치에서 app.invoke(None)으로 이어서 실행한다.
- ERPNext에서 실제 Cancelled 상태인 MR은 재시작하지 못하도록 막았다.
- 터미널 체크포인트가 남아 있으면 해당 결과를 DB에 다시 투영하여 화면 상태를 복구한다.
- 프론트의 실패 항목 재시도 버튼과 연결할 수 있는 API 동작을 준비했다.

이 작업으로 해결하려는 사례
- API Key 또는 외부 서비스 키 누락으로 AI 처리 중 실패
- 키를 넣고 서버를 재시작한 뒤 동일 MR을 체크포인트부터 계속 처리
- 이미 Submit된 MR이라는 이유만으로 재개가 막히는 문제 방지


8. 대체품 선택의 ERPNext-백엔드 연결
------------------------------------

- 요청 부서 사용자가 ERPNext Material Request 화면에서 대체품을 확인하고 선택할 수 있는 Client Script를 정리했다.
- 기존 스크립트의 localhost FastAPI 직접 호출은 다른 팀원 PC에서 동작하지 않고 CORS/포트포워딩 문제가 있어 제거했다.
- ERPNext 동일 출처의 Comment API를 이용하는 방식으로 변경했다.
- 사용자의 선택 결과는 MR Comment로 기록되고, 백엔드의 substitute reply poller가 이를 감지한다.
- 대체품 사용 선택 시 원 MR을 취소·종료하는 흐름으로 연결한다.
- 신규 구매 진행 선택 시 워크플로를 재개하고 구매 담당자에게 “신규구매 요청됨” 상태와 알림을 투영한다.
- 대체품 선택은 MR 검토 단계의 Draft 문서에서도 보이도록 조건을 조정했다.
- Client Script 생성 도구는 기존 스크립트를 삭제 후 재생성하지 않고 PUT으로 갱신하도록 변경했다.

주요 파일
- create_mr_substitute_client_script.py
- backend_logic2/api/mr_substitute_routes.py
- backend_logic2/nodes/mr/substitute_reply_watcher.py
- main.py


9. Item 목록과 규격 데이터
--------------------------

- Item 목록을 목 데이터가 아니라 ERPNext Item API에서 조회할 수 있는 엔드포인트를 구현했다.
- Item의 null 값 때문에 프론트에서 replace() 오류가 발생하지 않도록 데이터 정규화와 방어 처리를 보강했다.
- 규격은 ERPNext 문서의 모든 시스템 필드를 그대로 노출하지 않고 다음 우선순위로 추출한다.
  · 품목 그룹에 정의된 실제 규격 필드
  · ERPNext DocType 메타데이터상 사용자 입력 필드
  · PostgreSQL에 정의된 품목 그룹별 규격 스키마
- 예: 안전모는 “프리사이즈 54~63cm, 충격흡수 내피, 후면 래칫 조절, 4점식 턱끈, 색상 황색”처럼 사용자가 읽을 수 있는 규격 항목 위주로 표시하도록 준비했다.
- 프론트 규격 모달은 뭉친 문자열을 쉼표·줄바꿈·구분자 기준으로 임시 파싱해 항목별로 보여주도록 보강했다.
- Item 목록 검색은 코드, 품명, 요청부서, 규격 등 표시 데이터 기준으로 동작할 수 있게 연결했다.

10. RFQ, Supplier Quotation, 공급사 선정, PO
--------------------------------------------

- Supplier Quotation 조회 시 RFQ 연결 필드와 품목 자식 테이블을 확인하는 로직을 보강했다.
- 견적의 valid_till, 품목별 expected_delivery_date가 이후 비교와 PO 생성에 이어지도록 필드 전달을 정리했다.
- 공급사 추천 → RFQ 대상 선택 → 마감 연장 → 견적 확인 → 업체 선정 → 발주 시작 순서가 구분되도록 상태를 나눴다.
- 업체 선정은 자동 확정하지 않고 AI 추천 결과를 사람이 최종 선택하도록 유지했다.
- 업체를 선택한 뒤에는 같은 선정 버튼을 반복 노출하지 않고 “선정 완료”로 표시하며, 목록에서는 다음 상태를 보여주도록 했다.
- 발주 시작 시 협력사 선정 목록에서 제거되고 PO 관리 단계로 이동하도록 프론트 흐름을 정리했다.
- 기존의 별도 “협력사 승인 대기 PR” 목업 흐름은 현재 합의된 PO 전 사용자 승인 흐름과 구분했다.
- 공급사를 찾지 못했거나 PO 발송이 실패하면 성공처럼 넘기지 않고 협력사 선정 단계에서 오류와 사용자 개입 필요 상태로 표시할 수 있게 했다.
- 이메일이 없는 공급사는 자동 발송 대상에서 제외하되 사용자가 직접 이메일을 보완할 수 있는 폼 흐름을 고려했다.

ERPNext RFQ 포털 보강 준비
- 코어를 직접 수정하지 않고 Frappe custom app으로 포털 템플릿과 whitelisted method를 오버라이드하는 배포 파일을 준비했다.
- 포털 Supplier Quotation 작성 화면에 valid_till과 expected_delivery_date 입력을 전달하는 구조다.

11. Purchase Receipt 및 공급사 평가 연결
----------------------------------------

---------------------------------------

- 알림 드롭다운, 우측 하단 토스터, SSE 재연결을 연결했다.
- 사이드바를 접고 펼칠 수 있게 했다.
- 협력사 선정 완료 건은 선정 UI를 비활성/완료 상태로 바꾸고 다음 단계 액션만 노출하도록 정리했다.

13. 실시간 알림과 미접속 사용자 처리 원칙
------------------------------------------

- 실시간 이벤트만 프론트로 보내고 끝내지 않고 먼저 PostgreSQL에 상태와 알림을 저장한다.
- 사용자가 접속 중이면 SSE로 즉시 알림과 화면 갱신 신호를 받는다.
- 사용자가 미접속이면 DB에 그대로 남아 있다가 다음 로그인 시 REST 목록/알림 API로 한 번에 복구한다.
- SSE는 정답 데이터 자체가 아니라 “변경됨” 신호로 사용하고, 실제 화면 상태는 REST 재조회로 확정한다.
- SSE에 retry 지시자와 keep-alive를 적용했다.
- 서버 종료 시 대기 중인 PostgreSQL notification iterator를 취소·정리하여 Uvicorn 종료가 오래 걸리던 문제를 완화했다.
- 완료 작업은 즉시 물리 삭제하지 않고 종료 상태로 보존하여 AI 로그와 감사 이력을 검토할 수 있게 하는 방향으로 설계했다.

21. 대체품 응답 전 MR 조기 Submit 버그 수정
------------------------------------------

- 확인일: 2026-09-02
- 증상: 구매 담당자가 대체품 확인을 시작하면 요청자가 선택하기도 전에
  ERPNext MR이 Draft(docstatus=0)에서 Pending(docstatus=1)으로 바뀌고,
  Draft 문서에만 표시되는 “AI 대체품 확인” 버튼이 사라짐.
- 실제 확인 사례: MAT-MR-2026-00296, MAT-MR-2026-00297.
- 원인: Frappe는 일반 댓글뿐 아니라 담당자 할당과 상태 변경도 Comment
  DocType에 각각 Assigned, Label 유형으로 저장한다. AI 안내 댓글 직후
  자동 생성된 Assigned 이벤트에 “구매”라는 단어가 들어 있었고,
  substitute_reply_watcher가 이를 요청자의 신규구매 답변으로 잘못 파싱했다.
- 수정:
  · ERP 댓글 조회 시 comment_type=Comment만 가져오도록 제한
  · Client Script가 작성하는 “[BiddingFlow 대체품 선택]” 접두어가 있는
    댓글만 명시적인 사용자 결정으로 인정
  · 접두어 뒤의 후보 번호 또는 “구매” 값만 파싱
  · 일반 댓글, Assigned 이벤트, Label 이벤트는 그래프를 재개하지 않음
- 기대 흐름:
  · 대체품 후보 있음 → 안내/할당 → MR은 Draft 유지 → 요청자 선택 대기
  · 대체품 선택 → 원 MR 취소
  · 신규구매 선택 → 이 시점에만 MR Submit 및 후속 구매 흐름 재개
- 회귀 테스트:
  · 대체품이 있으면 _submit_mr_for_purchase가 호출되지 않는지 검증
  · Assigned/Label 이벤트가 선택으로 인식되지 않는지 검증
  · 마커 없는 “구매” 문구를 무시하는지 검증
  · Comment 조회 필터에 comment_type=Comment가 포함되는지 검증
- 검증 결과: 백엔드 전체 34개 테스트 통과.
- 주의: 이미 Pending으로 Submit된 MR은 ERPNext에서 Draft로 직접 되돌릴 수
  없다. 테스트 문서는 Cancel 후 새 MR을 만들거나 별도의 정리 절차가 필요하다.

33. 기존 MR 수정·첨부파일 증분 동기화
---------------------------------------

- 확인일: 2026-09-03
- ERPNext 원본 조회:
  · Material Request 상세 API에는 첨부파일 목록이 포함되지 않으므로, 연결된
    File 문서를 별도 조회해 `_attachments`로 합친 일관된 MR 원문을 사용한다.
  · 실제 ERPNext Draft MR을 읽기 전용으로 확인해 연결 File 1건이 함께 조회됨을
    검증했다.
- polling 모드:
  · 빠른 주기는 신규/수정 Draft MR을 확인하고, 별도 전체 정합성 주기는 이미
    워크플로우에 들어온 MR까지 다시 읽어 본문과 첨부파일 변경을 반영한다.
  · `MR_FULL_RECONCILE_INTERVAL_SECONDS`로 전체 정합성 주기를 조절한다.
- webhook 모드:
  · 기존 Material Request 웹훅에 더해 File 전용
    `/api/webhooks/erpnext/material-request-file` 엔드포인트를 추가했다.
  · File 이벤트는 Material Request 첨부만 수용하고 integration_event의 dedupe
    key로 재전송을 멱등 처리한다.
  · on_trash가 실제 삭제 전에 호출되어도 이벤트 원문의 File을 제외해 첨부 제거를
    즉시 투영한다.
  · 서버 재시작 시 한 차례 전체 MR 정합성 검사를 실행해 비접속 중 누락된
    변경도 복구한다.
- DB/프론트 반영:
  · 실제 투영 데이터가 달라졌을 때만 case를 갱신해 반복 polling의 불필요한
    version 증가와 DB 쓰기를 막는다.
  · 변경 시 MATERIAL_REQUEST_UPDATED 알림을 영속 저장하고 PostgreSQL NOTIFY →
    SSE를 통해 접속 중인 프론트 목록과 알림을 즉시 갱신한다.
