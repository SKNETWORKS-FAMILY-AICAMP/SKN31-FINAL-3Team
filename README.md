#### 1. 에이전트 설계 개요

BiddingFlow는 ERPNext의 구매 데이터를 기반으로 **대체품 탐색 → 비딩 판단 → 공급사 발굴 → RFQ 발송 → 견적서 추출·비교 → 수주 확인 → PO 발행**까지의 구매 실행을 지원하는 AI 구매 시스템입니다.

React·FastAPI·LangGraph를 중심으로 ERPNext, 외부 검색 도구, 견적서 추출 모델을 연결하며 대체품 사용, RFQ 대상, 최종 공급사 및 PO 승인 등 주요 의사결정 지점에는 담당자가 개입합니다.

#### 2. 멀티 에이전트 구성

| 에이전트 | 기술 스택 | 주요 역할 및 책임 |
|---|---|---|
| **구매 오케스트레이터** | LangGraph, FastAPI | MR과 사용자 응답을 상태로 관리하고 규칙 라우팅, `interrupt/resume`, 다음 구매 단계를 제어 |
| **대체품·공급사 탐색 에이전트** | ERPNext, Tavily, DART, Naver | ERP 품목·거래 정보를 조회하고 외부 검색을 통해 대체품과 연락 가능한 공급사 후보를 수집·보완 |
| **견적서 추출 에이전트** | Qwen3.5-9B, LoRA, RunPod | 이미지·PDF 등 비정형 견적서를 JSON으로 추출·정규화·검증하고 ERP Supplier Quotation Draft로 등록 |
| **견적 검토·정렬 에이전트** | Reviewer, Ranker | 규격·수량·산식·통화·유효기간을 검증하고 가격·납기·조건에 따라 유효 견적을 평가·정렬 |
| **수주·발주 실행 에이전트** | ERPNext API, Human-in-the-loop | 최종 공급사 선택과 공급사 수락을 확인한 뒤 PR·PO를 생성·제출·발송하고, 거절 시 차순위·재비딩으로 분기 |

#### 3. 서비스 및 연동 구조

```text
구매 담당자 · 구매 부서 · 공급사
               │
               ▼
      React 구매 업무 화면
               │ REST API / SSE
               ▼
         FastAPI 업무 API
               │
               ▼
    LangGraph 구매 오케스트레이터
       │          │           │
       │          │           └── RunPod / Qwen3.5-9B + LoRA
       │          └────────────── 외부 검색(Tavily · DART · Naver)
       └───────────────────────── ERPNext API / Webhook
               │
     PostgreSQL · 체크포인트 저장소
```

| 계층 | 구성 및 역할 |
|---|---|
| **사용자 화면** | React 구매 화면에서 케이스, 견적 순위, 승인 작업과 진행 상태 제공 |
| **서비스 계층** | FastAPI 업무 API와 SSE가 사용자 요청, ERPNext 웹훅 및 비동기 알림 처리 |
| **워크플로 계층** | LangGraph가 구매 단계를 제어하고 사람의 입력이 필요한 지점에서 실행을 대기·재개 |
| **업무 원천 데이터** | ERPNext가 MR, Item, Supplier, RFQ, Supplier Quotation, PO 등 구매 문서 관리 |
| **운영 데이터** | PostgreSQL이 구매 케이스, 작업, 알림, 검색 캐시, 회사 정책과 AI 판단 이력 관리 |
| **AI·검색 도구** | Qwen3.5-9B + LoRA가 견적서를 분석하고 Tavily·DART·Naver가 신규 공급사 정보를 보완 |

#### 4. LangGraph 오케스트레이션 및 상태 관리

각 노드는 `Command`로 상태와 다음 실행 위치를 지정합니다. 사용자 판단이 필요한 단계에서는 `interrupt`로 대기하고, 검증된 응답을 받은 뒤 `resume`하여 중단 지점부터 구매 흐름을 이어갑니다.

공유 State에는 다음 정보가 포함됩니다.

- **MR·품목 정보:** 구매요청 번호, 품목, 수량, 창고 및 대체품 후보
- **라우팅 상태:** 재고·대체품 결과, 비딩 여부, 다음 단계와 판단 근거
- **공급사·RFQ 상태:** 기존·신규 공급사 후보, 선택 공급사 및 RFQ 발송 결과
- **견적 상태:** 수신 견적, 검증 결과, 순위·제외 근거 및 최종 선택
- **수주·PO 상태:** 공급사 수락·거절, 차순위·재비딩 선택 및 PO 처리 결과
- **복구 식별자:** 체크포인트의 `thread_id`와 PostgreSQL의 `case_id`를 연결한 실행·업무 이력

#### 5. 전체 구매 Workflow

1. 구매 담당자가 ERPNext의 MR을 확인하고 구매 실행을 시작합니다.
2. ERP 품목·재고·구매 이력을 조회해 대체품을 추천하고 경쟁 구매 또는 직접 구매 경로를 판단합니다.
3. 공급사 후보가 부족하면 캐시와 외부 검색 도구로 기업·홈페이지·연락처를 보완합니다.
4. 담당자가 RFQ 발송 대상을 선택하면 ERPNext RFQ를 생성·발송하고 견적 회신을 기다립니다.
5. 이메일 첨부 견적은 Qwen3.5-9B + LoRA로 추출·검증한 뒤 ERP Draft로 등록합니다.
6. 포털·이메일 견적을 규격, 수량, 산식, 통화, 유효기간, 가격 및 납기 기준으로 검토·정렬합니다.
7. 구매 담당자가 최종 공급사를 선정하고 공급사의 수주 수락 여부를 확인합니다.
8. 공급사가 수락하면 승인 후 ERPNext PO를 생성·제출·발송합니다. 거절하면 차순위 요청, 재비딩 또는 종료 경로로 분기합니다.

#### 6. 장애 대응 및 신뢰성 설계

- **견적 검증 우선:** 추출 JSON은 정규화와 Pydantic 검증을 통과한 뒤 ERP Draft로 등록하며 이후 별도의 규칙 검토를 수행합니다.
- **부분 실패 기록:** 이메일 첨부파일별 처리 결과를 저장하고 일부 성공과 전체 실패를 구분하여 관리합니다.
- **체크포인트 복구:** 실행 상태와 오류·재시도 가능 여부를 기록하고 재개 가능한 지점부터 작업을 이어갑니다.
- **ERP 동기화 복구:** 폴링 실패는 다음 주기에 다시 시도하고, 웹훅 모드에서도 누락된 구매 문서를 재조정합니다.
- **검색 Fallback:** 공급사 정보가 부족하면 Tavily, DART, Naver를 단계적으로 활용해 후보와 연락처를 보완합니다.
- **Human-in-the-loop:** 대체품, RFQ 대상, 최종 공급사, 예외 처리와 PO 승인은 사람의 판단을 유지해 AI 오류가 자동 발주로 이어지지 않도록 합니다.

#### 7. 견적서 추출 모델 평가

동일한 내부 검증 데이터 100장과 13개 필드를 기준으로 측정한 결과입니다.

| 평가 대상 | 지표 | 결과 |
|---|---|---:|

| 문서 단위 정확도 | 채점 필드 완전일치 문서 | 84/100 |
| 추론 성능 | 평균 생성 시간 | 2.98초 |

> 내부 합성 데이터 분포에 대한 평가 결과이며, 실제 신규 양식과 필체에 대한 일반화 성능은 별도 검증이 필요합니다. 평균 생성 시간은 실행 환경의 영향을 받는 참고 지표입니다.

### 2.2 소개

BiddingFlow는 구매 요청(Material Request) 접수부터 재고 확인, 공급사 탐색, 견적 요청·수집, AI 견적 분석, 공급사 선정, 발주 및 사후 구매 문서 관리까지 이어지는 기업 구매 프로세스를 하나의 흐름으로 연결한 서비스입니다.

반복 가능하고 정책으로 정의할 수 있는 업무는 자동으로 처리하고, 예외 상황이나 승인이 필요한 단계에서는 담당자에게 판단 근거와 함께 작업을 전달합니다. 모든 단계와 AI 의사결정 기록은 대시보드에서 추적할 수 있습니다.

### 2.3 배경 및 선정 이유

기업의 구매 업무는 요청 확인, 재고 조회, 공급사 검색, 견적 요청, 문서 검토, 가격·납기·규격 비교, 발주 승인처럼 여러 시스템과 담당자를 오가는 반복 작업이 많습니다.

- 이메일과 문서 중심 업무로 인한 처리 지연 및 누락
- 비정형 견적서의 수작업 입력과 비교에 드는 시간
- 담당자별로 달라질 수 있는 공급사 평가 및 선정 기준
- 구매 단계별 진행 상황과 의사결정 근거 추적의 어려움
- ERP 데이터와 실제 구매 업무 사이의 단절

이러한 문제를 해결하기 위해 ERPNext 구매 데이터와 AI 문서 분석, 멀티 에이전트 워크플로를 결합했습니다. 자동화 가능한 단계는 시스템이 수행하고 사람이 필요한 시점에는 명확한 근거와 함께 개입하도록 설계하여 구매 업무의 **속도, 일관성, 추적 가능성**을 높이는 것이 목표입니다.


### 2.4 주요 기능 및 요구사항

| 구분 | 기능 | 설명 |
|---|---|---|
| **구매 요청** | MR 자동 수집 | ERPNext 구매 요청을 웹훅 또는 폴링 방식으로 동기화 |
| **구매 요청** | 재고·대체품 확인 | 현재 재고를 확인하고 구매 전 사용 가능한 대체품 추천 |

| **입찰** | RFQ 발송·회신 관리 | 공급사별 견적 요청, 제출 포털, 마감일 및 회신 상태 관리 |

| **워크플로** | 재입찰·예외 처리 | 재입찰 차수 관리와 담당자 검토가 필요한 예외 작업 제공 |

## 5. 실행 방법

### 5.1 사전 요구 사항

- Python 3.11 이상
- Node.js 20 이상 및 npm
- PostgreSQL
- 접근 가능한 ERPNext 인스턴스

### 5.2 백엔드 실행

```bash
python -m venv .venv

# Windows
.venv\Scripts\activate

pip install -r requirements.txt
copy .env.example .env
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

`.env`에서 ERPNext, PostgreSQL, JWT, RunPod 및 AI 서비스 환경 변수를 실행 환경에 맞게 설정해야 합니다. 실제 비밀키가 포함된 `.env` 파일은 커밋하지 않습니다.

### 5.3 프런트엔드 실행

```bash
cd frontend
npm install
npm run dev
```

| 서비스 | 로컬 URL |
|---|---|
| Frontend | `http://localhost:5173` |
| Backend API | `http://localhost:8000` |
| FastAPI Docs | `http://localhost:8000/docs` |
| Health Check | `http://localhost:8000/api/health` |

### 5.4 테스트

```bash
pytest -q

cd frontend
npm run lint
npm run build
```
