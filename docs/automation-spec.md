# 조건부 자동화 명세 (v2)

v1은 되돌렸다(`automation-v1-backup` 태그). 기능이 어려워서가 아니라 **실행
경로를 먼저 세우지 않고 판정부터 얹어서** 실패했다. v2는 순서를 뒤집는다.

---

## 0. 설계 원칙

**판정보다 실행 경로가 먼저다.** 그래프를 부르는 주체가 사람 하나에서 여럿
(마감 스캔, 견적 도착, 규격 평가 완료)으로 늘어나는 순간 잠금·스레드·요청
제한이 한꺼번에 드러난다. v1은 그걸 증상이 보일 때마다 한 겹씩 덮다가
난잡해졌다. v2는 실행 경로를 먼저 만들고 지금의 **수동 흐름으로 검증한 뒤**
그 위에 판정을 얹는다.

**마감 시각은 "판정 시점"이 아니라 "판정을 시작해도 되는 조건"이다.**

> 마감이 지났고 **＋** 마감 전에 제출된 견적이 전부 처리 완료(파싱 + 규격
> 평가)됐을 때 판정한다.

이러면 스케줄러가 10분 뒤에 돌든 30초 뒤에 돌든 **결과가 같다.** 주기는
정확성이 아니라 반응 속도의 문제로 내려간다. 규격 평가가 아직 돌고 있으면
그냥 "조건 미충족"이라 기다리는 것이지 별도 예외 처리가 아니다.

**사건이 끌고 가고, 스캔은 안전망이다.** 마지막 견적이 도착했을 때와 마지막
규격 평가가 끝났을 때(RunPod 웹훅) 그 자리에서 조건을 다시 본다. 보통은
마지막 조각이 채워진 직후 몇 초 안에 판정이 돈다.

**애매하면 사람에게 넘긴다.** 값을 알 수 없을 때도 통과가 아니라 정지다.

## 1. 전체 흐름

```
MR 수신(폴링 5초)
  └ 실행 / 반려                                    ← 사람 (기존과 동일)
      └ 품목·대체품 확인
          └ 비딩 여부 판단
              ├ 비딩 불필요 → 직접구매 / 구매 중단  (기존과 동일)
              └ 비딩 필요
                  └ 공급사 풀 판정
                      ├ 기존 풀로 충분  → RFQ 자동 발송      ← 자동
                      └ 신규 탐색 필요  → 협력사·마감일 선택  ← 사람(handle)
                          └ RFQ 발송
                              └ 견적 수집 … 마감
                                  └ 평가 → 순위 → 조건 판정
                                      ├ 통과   → 선정 + PR 발송  ← 자동
                                      └ 미통과 → 최종 선정 화면   ← 사람
                                          └ 선정 + PR 발송
                                              └ 수주 접수 확인
                                                  └ PO 승인·발송 ← 사람
```

사람이 멈추는 곳은 **실행/반려 · (신규 탐색 시) 협력사 선택 · (조건 미통과 시)
최종 선정 · PO 승인** 네 군데다.

## 2. 선행 수정

### 2-1. 기다리는 노드가 자기 상태를 세운다

기존 풀로 충분해서 `select_rfq_targets`로 바로 오면, 케이스 상태가
`resolving_supplier_pool`(단계: 협력사 탐색)에 머문 채 사람을 기다린다.
화면은 `RFQ_TARGET_SELECTION`에서만 버튼을 열기 때문에 **그래프는 답을
기다리는데 화면은 막혀 있다.**

`ae188dd`부터 있던 문제고 자동화와 무관하다.

> **정정**: 처음엔 "기다리는 노드가 `interrupt()` 직전에 스스로 상태를 세운다"로
> 적었는데 **불가능하다.** LangGraph는 노드가 `Command`를 반환할 때만 state를
> 갱신하므로, `interrupt()`로 멈추는 노드는 자기 상태를 남길 방법이 없다.

그래서 **투영이 멈춰 선 지점에서 단계를 도출한다**(`project_waiting_point`).
인터럽트가 걸려 있으면 직전 노드가 남긴 `status`가 아니라 그 대기 지점의
종류로 단계를 정한다. 호출하는 쪽마다 상태를 세우게 하면 경로가 늘 때마다
같은 실수가 반복되지만, 이렇게 하면 어느 경로로 들어오든 맞는다.

대기 지점을 새로 추가하고 표에 안 넣으면 조용히 옛 동작으로 돌아가므로,
**소스에서 실제 인터럽트 타입을 뽑아 표와 대조하는 테스트**로 막는다.

## 3. 실행 경로 (먼저 만들고 수동으로 검증한다)

그래프 한 번은 몇 분이 걸릴 수 있다(ERPNext 쓰기, 메일 발송, 공급사 검색).
실패는 전부 "그걸 누가 어디서 기다리느냐"에서 나왔다.

- HTTP 요청 안에서 기다림 → nginx `/api/` 60초 제한에 걸려 504. 화면에는
  "구매 작업 API 요청에 실패했습니다"만 남고, 그래프는 계속 돌아서 케이스가
  "…중"에 갇힌다.
- `BackgroundTasks`에서 기다림 → 동기 엔드포인트와 같은 스레드풀(40개)을
  먹어서, 쌓이면 로그인까지 막힌다.
- async 라우트에서 기다림 → 이벤트 루프가 멈춰 서버 전체가 먹통.
- 폴러 스레드에서 기다림 → 잠금을 쥔 채 다른 경로를 줄 세운다.

**규칙: 자동 경로가 그래프를 돌릴 때는 전용 워커에 예약만 하고 즉시 돌아온다.
사람이 누르는 경로는 지금 동작을 그대로 둔다.** 사람 경로는 몇 주간 쓰던
검증된 길이라 건드리지 않는 것이 가장 안전하다.

지켜야 할 것:

- **케이스 잠금은 기다리지 않는다.** 못 잡으면 건너뛰고 다음 턴에 다시 본다.
  기다리는 잠금은 스캔 전체를 세우고, 그 뒤 스캔까지 연쇄로 막는다.
- **`RUNNING` 표시만 보고 막지 않는다.** 그 표시는 DB에 남고 실제 작업은
  메모리에 있다. 재시작이나 예외로 작업이 사라지면 표시만 남아 케이스가
  영구히 잠긴다. 실제로 도는지를 따로 추적해 판단한다.
- **폴러가 워커를 차지하지 않는다.** 조회는 폴러 스레드에서 하고, 그래프
  실행만 워커로 넘긴다.
- **상황이 그대로면 재평가하지 않는다.** 경로와 무관하게 적용한다.
- **결과는 화면에서 보인다.** 서버 로그를 못 보므로 판정·대기·실패 이유가
  전부 AI 판단 기록에 남아야 한다.
- **재시작 복구.** 워커 큐는 메모리에만 있다. 기동 시 `RUNNING`/`PROCESSING`
  으로 남은 건을 체크포인트 기준으로 되돌린다.
- **DB 결과는 컬럼 이름으로 읽는다.** `row_factory=dict_row`라 `fetchone()[0]`
  은 `KeyError(0)`이다. v1의 마감 스캔이 이것 때문에 한 번도 못 돌았다.
- **가짜 연결도 진짜처럼 딕셔너리를 돌려준다.** 튜플을 쓰면 실제로는 죽는
  코드가 테스트를 통과한다.

## 4. RFQ 자동 발송

**조건**: 비딩 필요 + 공급사 풀 판정이 "기존 풀로 충분" + 후보 전원 이메일 확인.
하나라도 어긋나면 기존 협력사 선택 화면(handle)으로 간다.

- "기존 풀로 충분"의 기준 수는 **회사 정책의 새 값**으로 둔다
  (`min_competing_suppliers`와는 다른 질문이라 분리).
- **재비딩(2차 이상)은 자동 발송하지 않는다.** 사람이 재비딩을 고른 건 1차에서
  뭔가 잘못됐기 때문인데, 같은 후보에 같은 조건으로 다시 보내면 그 잘못을
  반복한다.
- **자동화가 재비딩을 선택하는 경우는 없다.** 자동 판정의 결과는 "조건 통과 →
  진행" 아니면 "사람 호출" 둘뿐이다. 재비딩은 사람이 예외 결정 화면에서
  고르는 선택지다.

**마감일**: `발송 시각 + N일`의 **18:00**. N은 회사 정책값.
납기요청일이 있으면 `min(N, 납기까지 남은 일수)`, 없으면 N 그대로.

> 비딩에 들어온 건은 납기가 최소 8일 남아 있다(납기 ≤ 7일이면 긴급으로
> 분류돼 비딩에 오지 않는다). 납기일이 아예 없는 MR만 긴급 판정을 건너뛰어
> 비딩에 올 수 있고, 그때는 제약이 없으므로 N을 그대로 쓴다.

## 5. 최종 선정 자동화

**판정 시작 조건**: 마감이 지났고, 마감 전 제출분이 전부 처리 완료.
또는 전원이 회신했고 그 전부가 처리 완료.

**제출 시각의 기준** — 견적은 포털과 이메일 회신 두 경로로 들어온다.
**협력사가 낸 시각**이 기준이다. 우리가 처리한 시각이 아니다.
17:59에 낸 견적이 우리 처리가 밀려 18:03에 반영돼도 **포함**하고,
18:01에 낸 건 **버린다**.

- 포털: Supplier Quotation의 생성 시각.
- 이메일: Communication의 `communication_date`(없으면 `creation`).

이 값은 지금 어디에도 남지 않으므로 우리 DB에 따로 기록한다.

**규격 평가가 안 끝났으면** 사람을 부르지 않고 기다린다. 대기 한도는 지금
두지 않는다(실측 1분 이내). 대신 **대기 중이라는 사실이 화면에 보이게** 한다 —
조용히 멈춰 있는 것이 v1에서 가장 나빴던 부분이다.

**사람을 부르는 조건(exception)**:

| 조건 | 뜻 |
|---|---|
| 경쟁 견적 부족 | 유효 견적이 정책 최소치 미만 (단독 응찰 포함) |
| 점수차 미달 | 1·2순위 종합점수 차이가 정책값 미만 |
| 금액 초과 | 선정 금액이 정책 상한 초과 |
| 신규 협력사 | 1순위에게 **최근 3년 내 확정 발주 이력이 없음** |
| 감점 확인 필요 | 1순위에 확인이 필요한 감점 |
| 견적 유효기간 경과 | 1순위 견적의 유효기간이 지남 |
| 회신 0건 | 마감인데 아무도 회신하지 않음 (**자동 연장하지 않는다**) |

조건을 전부 통과하면 **선정 + PR 발송까지 자동**. 하나라도 걸리면 기존 최종
선정 화면으로 사람을 부르고, 사람이 선정하면 기존대로 팝업에서 PR까지 보낸다.

**차수와 무관하게 적용한다.** 2차 이상(재비딩)도 RFQ 발송만 사람이 하고,
그 뒤 선정 판정은 1차와 똑같이 돈다.

### 5-1. 수동 버튼

마감을 기다리지 않고 **지금 평가·순위·조건 판정을 돌려 결과만 보여준다.**
마감 전이면 **진행하지 않는다** - 아직 견적을 낼 시간이 남은 협력사가 있는데
먼저 닫아버리는 일이 없어야 한다. 실제로 닫고 싶으면 **"지금 마감"** 으로
마감일을 현재로 당긴 뒤 정상 경로를 탄다(상태를 속이지 않는다).

> v1의 이 버튼은 마감 전에도 "마감이 지났다"고 그래프에 전달해서, 켜짐
> 모드에서 누르면 조기 선정이 될 수 있었다.

> 조건에 걸린 건은 견적을 확정(Submit)하지 않는다. 확정은 되돌리기 어렵다.

## 7. 회사 정책에 추가되는 값

| 값 | 기본 | 뜻 |
|---|---|---|
| 자동 진행 모드 | 꺼짐 | 꺼짐 / 기록만 / 켜짐 |
| RFQ 자동 발송 | 켬 | 단계별 스위치 |
| 최종 선정 자동화 | 켬 | 단계별 스위치 |
| 기존 풀 충분 기준 | 3곳 | 이 이상이면 신규 탐색 없이 자동 발송 |
| 자동 발송 마감 N일 | 5일 | 발송 시각 + N일 18:00 |
| 자동 선정 최소 견적 수 | 2건 | 최솟값 2 — 단독 응찰은 어떤 설정으로도 자동 선정되지 않는다 |
| 자동 선정 최소 점수차 | 10점 | 1·2순위가 붙으면 사람에게 |
| 자동 선정 금액 상한 | 5,000만원 | 넘으면 사람에게 |
| 거래 이력 인정 기간 | 3년 | 이 안에 확정 발주가 없으면 신규 협력사 |

정책은 케이스마다 고정된다. 진행 중인 건은 설정을 바꿔도 영향받지 않는다 —
운영 중 서비스가 갑자기 움직이지 않게 하는 안전장치다.

## 8. 만드는 순서

1. **선행 수정**(2-1) — 기다리는 노드가 자기 상태를 세운다.
2. **실행 경로**(3) — 자동 경로용 전용 워커, 케이스 잠금, 재시작 복구.
   **자동화 없이** 지금의 수동 흐름으로 검증한다.
3. **정책값**(7) — 기본 꺼짐.
4. **RFQ 자동 발송**(4) — 기록만 모드로 검증 후 켜짐.
5. **최종 선정 자동화**(5) — 기록만 모드로 검증 후 켜짐.

각 단계마다 되돌리면 테스트가 실패하는지 확인한다. 통과만으로는 부족하다 —
v1에서 가짜 연결이 튜플을 돌려주는 바람에, 실제로는 반드시 죽는 코드가
테스트를 통과했다.
