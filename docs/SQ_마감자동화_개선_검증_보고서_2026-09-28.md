# 견적 마감 자동화 개선·검증 보고서

작성일: 2026-09-28

대상: BiddingFlow 백엔드 / 기존 main `8f254e7` 기준

범위: 마감 감시의 반복 조회·실행 대기 문제 개선. 기존 구매 판단 기준과 승인 절차는 유지.

## 1. 쉽게 보는 개요

### 무엇이 문제였나요?

자동화하려던 일은 “견적 마감이 됐고 분석도 끝났으면 다음 단계로 진행”입니다. 이 목표는 정상적입니다.

문제는 확인 방법이었습니다. 이전에는 견적 대기 건들을 반복해서 검사하면서 ERPNext에서 요청서와 견적 상세를 매번 다시 가져왔습니다. 같은 상태를 이미 판단했는지 확인하는 장치도 있었지만, 비싼 조회가 끝난 뒤 확인했습니다.

게다가 전체 검사를 실제 구매 업무와 같은 단일 실행 통로에 넣었습니다. 사무실의 담당자 한 명에게 “대기 서류 전체 재검토”를 맡긴 동안 새로 들어온 업무가 줄을 서는 모습입니다. 실제 그래프 실행의 공통 잠금까지 겹치면 사용자가 누른 버튼도 기다리다가 504를 만날 수 있었습니다.

확인된 사실은 반복 조회와 실행 경로의 병목입니다. 과거 장애 당시 CPU 포화나 DB 연결 고갈까지 확정한 것은 아닙니다.

### 무엇을 고쳤나요?

| 이전 | 개선 |
|---|---|
| 일정 간격으로 전체 건의 ERP 서류 재조회 | DB에서 변경된 입력을 찾아 마감 작업 예약 |
| 이미 확인했는지 늦게 검사 | 같은 입력의 WAITING/DONE 작업은 외부 조회 전에 제외 |
| 전체 스캔이 그래프 실행 통로 점유 | 별도 준비 담당이 한 건씩 검사, 그래프에는 준비된 한 건만 전달 |
| 분석 중인 첨부를 놓칠 가능성 | DB에 남은 첨부 추출 작업이 끝나기 전 진행 금지 |
| 요청 처리용 스레드에서 긴 견적 분석 실행 | 별도 실행기로 전달, 기존 202 접수 응답 유지 |
| 사용자 작업이 공통 잠금을 장시간 기다림 | 해당 작업 재개 경로는 즉시 “처리 중, 다시 시도” 응답 |
| 서버 재시작 후 실행 여부가 불분명 | 예약·준비·실행 상태를 DB에 보관, 불확실한 실행은 자동 재발송 금지 |
| 중지하려면 코드 수정·재배포 | 관리자 API로 DB 스위치 변경, 신규 실행 즉시 차단 |

예를 들어 RFQ 하나에 견적 10개라면 기존 준비 검사에는 ERP 조회 12회가 필요했습니다. 새 방식에서도 처음 필요한 검사는 이 조회를 할 수 있습니다. 차이는 **변화가 없다면 다음 주기에는 같은 조회를 다시 하지 않는다**는 것입니다. ERP API 자체를 일괄 조회 API로 바꾼 것은 아닙니다.

### 팀원들의 작업과 충돌하지 않나요?

- 기존 `deadline_readiness`, `auto_progress`, `resume_task`와 작업 버전 확인을 재사용합니다.
- 최종 선정 조건, 회사 정책, 반려·재비딩·사람 승인 경로를 새 기준으로 교체하지 않았습니다.
- 케이스에 고정된 정책을 유지합니다. 관리자 정책 변경을 과거 MR에 강제로 적용하지 않습니다.
- 기존 수동 “자동 진행 판정” 버튼은 유지합니다.
- TEST_MODE, 수신 화이트리스트, ERPNext 문서, 실제 메일은 이번 검증에서 변경하지 않았습니다.
- 기존 로컬 입고 QA 수정 3개 파일은 별도로 보존하며 이번 커밋에 섞지 않습니다.

### 배포되면 바로 모든 MR이 자동으로 진행되나요?

아닙니다. 새 스케줄러는 안전하게 기본 OFF입니다.

인스턴스 환경변수와 DB 관리자 스위치를 둘 다 켜야 예약 처리가 실행됩니다. 개발 PC와 운영 서버가 같은 DB를 보더라도, 개발자가 pull한 것만으로 자동 진행이 시작되지 않게 했습니다. 실제 진행 여부는 여기에 더해 해당 MR에 고정된 회사 정책의 자동화 조건을 따릅니다.

이번에는 관리자 **API**를 추가했습니다. 프론트 관리자 화면에 새 토글 UI를 추가한 것은 아닙니다.

## 2. 기술 구조

### 예약 담당: DB만 확인

`deadline_scheduler.tick()`는 30초마다 실행됩니다. 이 함수에서 ERPNext·RunPod를 호출하거나 그래프 완료를 기다리지 않습니다.

1. 인스턴스 허용과 DB 운영 스위치 확인
2. 만료된 준비 작업 복구
3. 변경된 입력 최대 50건 조회
4. DB 연결 하나·SQL 하나로 예약 일괄 저장
5. 준비 실행기가 비어 있으면 기한이 된 한 건 점유
6. 준비된 작업이 있고 그래프 실행기가 비어 있으면 한 건 전달

주기적 확인 자체를 없앤 것은 아닙니다. **ERP 전체 스캔을 가벼운 DB 예약 확인으로 바꿨습니다.** 정확히 마감 초에 실행되는 메모리 타이머도 아닙니다. 30초 확인 주기와 준비·대기 시간만큼 지연될 수 있습니다. 준비 작업은 인스턴스당 동시에 한 건으로 제한합니다.

### 입력 지문: 무엇이 바뀌면 다시 확인하나요?

`quotation_deadline_input` 뷰는 다음 DB 입력으로 변경 지문을 계산합니다.

- 현재 RFQ, 이전 RFQ 차수, 마감 시각
- 견적 목록·회신 현황 스냅샷
- 케이스에 고정된 정책 버전
- 규격 평가 캐시의 견적 ID·입력 해시·평가 모델·결과
- 제출 시각과 출처
- 첨부 추출 작업의 ID와 상태
- 견적 읽기 실패 기록
- SQ 웹훅으로 받은 RFQ별 변경 revision

단순히 “견적 3개, 캐시 3개”를 비교하지 않습니다. 같은 개수라도 다른 견적·내용·평가 모델이면 다시 확인합니다.

케이스 updated_at/version은 지문에서 제외했습니다. 화면 투영만 바뀌어도 자동 진행을 반복하는 일을 막기 위해서입니다. 평가 캐시 updated_at도 제외해서 **같은 평가 결과를 다시 저장한 것**만으로 반복 실행되지 않게 했습니다.

지난 차수의 SQ 수정·삭제도 RFQ 변경 revision으로 감지합니다. 중복 웹훅은 기존 이벤트 중복 방지 경로에서 제외됩니다.

### 준비 담당: 외부 조회를 별도 실행기에서

`_prepare()`는 전용 스레드 한 개에서 실행합니다. 그래프 실행 대기열이나 전역 그래프 잠금을 점유하지 않습니다.

- 입력이 바뀌었거나 사용자가 먼저 진행했다면 폐기
- 마감이 없으면 설정될 때까지 대기
- 첨부 추출이 진행 중이거나 제출 여부가 불확실하면 대기
- 케이스 정책의 자동화가 OFF이면 외부 조회 없이 종료
- 필요한 경우 ERP 기반 검증을 한 번 수행
- 동일 검증 결과를 readiness 판단에 전달하여 중복 조회 방지
- 검사 후 입력 지문을 다시 확인하고, 중간에 바뀌었다면 결과 폐기
- AI 규격 평가가 아직 끝나지 않았으면 WAITING으로 저장

WAITING은 다음 주기마다 ERP를 다시 읽지 않습니다. 평가 캐시·견적·첨부 처리 상태 등 관련 입력이 바뀌면 다시 예약됩니다. DB 변경을 다음 tick에서 확인하므로 프로세스가 잠시 꺼져 있어도 변경을 놓치지 않습니다.

새 자동 경로는 `validate_case_quotations(strict=True)`를 사용합니다. 캐시나 실패 기록을 읽지 못했을 때 증거가 없는 상태를 성공으로 간주하지 않고 제한적으로 재시도합니다. 기존 수동 화면의 기본 호환 동작은 유지합니다.

### 실제 진행 담당: 준비된 한 건만 기존 그래프에 전달

`graph_worker.try_submit_idle()`은 그래프 실행기에 대기·실행 중 작업이 없을 때만 자동 작업 한 건을 받습니다. 전체 스캔을 작업 하나로 넣지 않습니다.

실행 직전 다시 확인합니다.

- 운영 스위치와 인스턴스 허용
- 입력 지문과 미완료 첨부 존재 여부
- 현재 케이스 단계·상태
- 현재 서버의 SQLite 체크포인트 존재 여부
- 대기 작업과 최신 버전
- 건별 advisory lock
- DB 상태 변경의 비교 후 갱신(CAS)

그 뒤에만 기존 `resume_task()`를 호출합니다. 기존 정책 노드가 실제 자동 선정 가능 여부를 판정합니다.

체크포인트는 여전히 기존 SQLite입니다. PostgreSQL 체크포인트 전환이나 여러 서버에서 그래프를 병렬 실행하는 구조까지 이번에 변경하지 않았습니다.

## 3. HTTP 응답 및 과부하 방어

### 사용자 요청용 스레드 보호

수동 견적 분석은 기존처럼 HTTP 202를 반환합니다. BackgroundTasks는 이제 긴 분석을 직접 수행하지 않고 전용 실행기에 넘긴 후 끝납니다.

- 전용 실행 스레드: 1개
- 실행 중 + 대기 중 합계: 최대 8개
- 꽉 차면 작업 점유 전에 409 응답
- 정상 완료·실패 때 슬롯 반환
- 실행기 예약 실패 시 작업 점유와 상태 복구

RFQ 전송 등을 처리하는 `resume_task()`에서는 공통 잠금을 기다리지 않고 확보할 수 있는지 즉시 확인합니다. 다른 작업이 점유했다면 기존 409 오류 경로로 “요청은 실행되지 않았으며 잠시 후 다시 시도”를 알립니다. 버튼을 눌렀는데 응답 없이 60초 기다리는 상황을 줄입니다.

**모든 구매 API를 202 방식으로 전환한 것은 아닙니다.** RFQ 전송 자체의 ERP/메일 처리가 오래 걸리는 문제까지 전부 해결했다고 보장하지 않습니다. 이번 변경은 특히 배경 작업 때문에 앞에서 기다리는 문제를 다룹니다.

### 제한과 복구

- 준비 검사: ERP 최대 100회, 30초 기준 호출 예산
- 예산 소진 시 추가 ERP 호출 금지, 개별 요청 timeout도 남은 예산에 맞게 축소
- requests의 읽기 timeout은 전체 작업 강제 종료가 아니므로 정확한 30초 hard-kill을 보장하지 않음
- 준비 실패: 최대 3회, 재시도 대기 120초·240초 후 한도 초과 시 BLOCKED
- 준비 점유: 5분 lease, 만료 시 토큰을 바꿔 안전한 준비 작업만 복구
- 실행 중 작업: 30분 lease, 만료 시 UNCERTAIN으로 두고 자동 재실행 금지
- 예약 DB 문장: statement_timeout 3초, lock_timeout 0.5초
- 기존 업무 그래프에는 준비 검사의 30초 예산을 강제로 적용하지 않음

이미 메일이나 ERP 쓰기가 일어난 뒤 오류가 날 수 있으므로, 실행 중단 건을 자동으로 재시도하여 이중 발송하지 않도록 보수적으로 처리했습니다. UNCERTAIN은 기존 수동 화면과 실제 ERP 진행 상태를 확인할 대상입니다.

## 4. 저장 상태

| 상태 | 의미 | 다음 처리 |
|---|---|---|
| PENDING | 마감 또는 재시도 시각 대기 | 기한이 되면 준비 담당이 점유 |
| CHECKING | 읽기 전용 준비 검사 | 결과를 READY/WAITING 등으로 저장 |
| READY | 입력이 준비되어 실행 대기 | 실행 직전 재검증 |
| RUNNING | 기존 그래프 진행 중 | 완료 또는 불확실 상태 기록 |
| WAITING | 첨부·AI 평가·마감 정보 대기 | 관련 입력 변경 시 재예약 |
| DONE | 해당 입력에 대한 판단 완료 | 관련 입력 변경 시 재예약 |
| BLOCKED | 반복 실패·체크포인트 부재 등 | 수동 확인; 입력 변경 시 재검사 가능 |
| UNCERTAIN | 실제 부작용 발생 여부 확인 필요 | 자동 재실행하지 않음 |

메일 발송까지 포함한 분산 시스템의 “정확히 한 번 실행”을 보장한다고 주장하지 않습니다. 작업 점유·버전 검증·입력 지문·보수적 복구로 중복 실행 위험을 줄였습니다.

## 5. 관리자 제어 및 운영 확인

### 최초 활성화

1. 마이그레이션 025가 적용되었는지 확인합니다. 기존 배포 스크립트는 테스트 후 마이그레이션을 수행합니다.
2. 실제 그래프 체크포인트가 있는 운영 인스턴스에서만 아래 환경변수를 설정합니다.

```dotenv
DEADLINE_SCHEDULER_ENABLED=true
```

3. 환경변수 변경 반영을 위해 서비스 재시작이 한 번 필요합니다.
4. 관리자 인증으로 `POST /api/company-policy/deadline-scheduler`를 호출합니다.

```json
{"enabled": true, "reason": "검증 완료 후 마감 자동 판정 활성화"}
```

5. `GET /api/company-policy/deadline-scheduler`에서 control.enabled와 runtime.instance_enabled가 모두 true인지 확인합니다.
6. 활성화하면 새 MR뿐 아니라 기존 대기 건도 대상이 될 수 있으므로, 남아 있는 테스트·운영 건과 케이스별 정책을 먼저 확인합니다.

기존 로그인 인증과 ERPNext 관리자/구매 정책 관리 권한 검사를 재사용합니다. 토큰을 URL이나 보고서에 넣지 않습니다.

### 재배포 없이 중지

동일 POST API에 다음 내용을 보냅니다.

```json
{"enabled": false, "reason": "운영 점검을 위해 신규 자동 실행 중지"}
```

설정은 즉시 DB에 저장됩니다. 다음 준비·실행 진입 시 재확인하며, 이미 시작된 메일/ERP 업무를 강제로 취소하는 스위치는 아닙니다. 이 DB 스위치 변경에는 재시작이 필요 없습니다.

### 상태와 로그

GET 응답에는 관리자 설정, 마지막 tick, 준비 실행 여부, 그래프 대기·실행 수, 상태별 건수, 최근 작업 최대 50건과 사유·지표가 있습니다.

- 준비: elapsed_ms, erp_calls, db_connections
- 그래프: graph_ms, graph_erp_calls, graph_db_connections
- 실행 대기: queue_wait_ms
- 로그 식별자: deadline_tick, deadline_prepare, deadline_prepare_failed, deadline_execute_failed

DB 연결 지표는 해당 측정 구간의 연결 생성 시도 수이며, 서버 전체 동시 연결 수가 아닙니다. ERP 호출 수도 공용 ERP 세션을 통한 호출 범위입니다. 문서 본문·API 키는 지표에 저장하지 않습니다.
